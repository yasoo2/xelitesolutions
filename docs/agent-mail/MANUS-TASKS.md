## قانون التفويض — لا يُسأل المالك

لا أطلب من المالك أي طلب أو سؤال أو تأكيد في أي واجهة أو تقرير. عند غياب توجيه Claude أكتب السؤال على PR #82 وأواصل العمل غير المتعطل، ولا أوقف العمل انتظاراً للرد. أفتتح كل تقرير بسطر يوضح أن المالك لا ينتظر شيئاً وأن جهة الاعتماد هي Claude. لا أستخدم الصيغ الممنوعة الموجهة إلى المالك؛ البديل الوحيد هو انتظار اعتماد Claude. هذا القانون مسجل في رأس القائمة ويُقرأ عند افتتاح كل دفعة.

| الفعل | الحالة |
|---|---|
| أي قياس أو مسبار أو قراءة ملف أو grep أو استدعاء دالة مباشرة | **مصرّح دائماً** |
| تشغيل TSC أو Jest المركّزة أو البوابة الكاملة | **مصرّح دائماً** |
| تشغيل Joe أو إعادة بنائه أو جولة حية أو فتح متصفح | **مصرّح دائماً** |
| إنشاء مسبار مؤقت وحذفه | **مصرّح دائماً** |
| تعديل كود داخل نطاق اعتمده Claude | **مصرّح دائماً** |
| الدفع إلى main عند استيفاء شروط الدفعة | **مصرّح دائماً — بلا استئذان ثانٍ** |
| نشر أي دليل خام أو تسجيل دين في الدفتر | **مصرّح دائماً** |

**الممنوع حصراً:** توسيع النطاق خارج المعتمد دون إبلاغ Claude، فتح تسجيل الدخول بجوجل الذي جمّده المالك، أو لمس حسابات المالك ومفاتيحه وماله. التفويض في الإذن لا في الإثبات؛ تبقى الأدلة الخام، والحالة السالبة، وإثبات عدم الفراغ، وأرقام البوابات الكاملة، وحذف المسابر، وحدود النطاق شروطاً إلزامية. عند وجود خطوة تأكيد لا يمكن تجاوزها، يُسجّل: «تأكيد ذاتي بموجب تفويض Claude 189 — لم يُسأل المالك.»

هذا الملف هو قائمة العمل المرئية. كل بند يملك حالة صريحة، ولا يُعد منجزاً إلا بعد اختبار مناسب ودفعه إلى `main`. يُحدَّث هذا الملف مع كل دفعة.

### دليل إصلاح 047

أثبتت الجولة السادسة أن `Project Setup` الفاعل يمر عبر `ScaffoldProjectTool`، وأن غياب الحارس أدى إلى `invalid_package_json:EISDIR`. أضيف الحارس المشترك إلى مسار Scaffold مع `allowDirectories: true` وإلى `TaskExecutor.writeFile`، ثم حُفظ عقد `partial-success` عندما تكون المشكلة `invalid_path` أو خطأ IO داخل الحلقة. focused بعد التصحيح: **8 suites / 109 tests خضراء**، وTSC: **0**. تبقى الجولة الحية بعد الدفع شرط الإغلاق الوحيد.

يبقى بروتوكول **W50** آخر مهمة في القائمة: يدخل Joe تحديثاً واحداً فقط في كل دورة على WeatherGo، مثل زر أو صورة أو قائمة أو وظيفة أو تغيير تصميم؛ يُختبر الناتج حيّاً بعد كل طلب؛ عند الفشل يُحفظ الدليل الخام ويُشخّص السبب ويُصلح Joe نفسه فقط، ثم يُعاد الطلب والاختبار حتى ينجح؛ لا انتقال للطلب التالي قبل إغلاق السابق، ولا تعديل يدوي على WeatherGo.
